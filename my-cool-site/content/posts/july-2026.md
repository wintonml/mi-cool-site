Writing up documentation can be quite boring. It is easy to put it off later and do it once you are done working on your
current item. However, there's always another item! So the best time to write documentation is now, because documentation is 
your friend. 

In my workflow, documentation is one of the first things I do. When working on a task, I will start writing test plans to show
the system's existing behaviour. In my test plans, I mention key features and values necessary to reproduce the bug, 
screenshots of pages and values for evidence, and any queries that help find test data or show important values related to the 
feature being developed. There are many reasons to do this, but the two main reasons for me are that it shows an understanding 
of the task and it helps others (or my future self) reproduce it.

There were many times early on in my career where I would think "this is easy enough, I'll remember how to do this." Then 
many months later I'll get asked to reproduce the behaviour and I'd have to spend time refamiliarising myself with it.

Alongside the test plans, I write dev notes where I record important functionality of the system being altered and the 
reasoning behind the changes. While it is important to note the changes being made, it's just as important to explain why they 
were made. While hopefully the code you are producing is error-free, most likely it won't be. By recording the reasoning for 
the changes you are helping a future developer understand the code without having to reverse-engineer it.
Other places to record this information include code reviews and comments within the code.

While having all this documentation is good, you need to make sure it is easy to find! Attach it to your tickets, mention 
them in your code reviews, and share them with others if it will be useful for them. There is no point in writing it all up 
if it can't be found.  

The reason I think of this so much is that the items I've recently worked on are years old and the tickets have a 
brief description of the problem. Because of that, I often wish that there were notes describing how to reproduce the issue, 
what the system looked like at the time, and any gotchas to be aware of. If that is something I want other developers to do,
that must be something I should do myself to save the time and effort of others.

So be kind to others and write some documentation.
